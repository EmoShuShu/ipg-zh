6. IPG 原生内容模型与注解锚点

正式 YAML 仍按可审阅文件拆分，但版本目录使用组合 release ID，而不是只用官方日期：

src/ipg/
  current-release.txt
  display-values.yaml
  id-registry.yaml
  mapping-overrides.yaml
  releases/<release-id>/
    manifest.yaml
    front-matter.yaml
    chapter-01.yaml ... chapter-04.yaml
    appendix-a.yaml
    appendix-b.yaml

2.5 的代表性结构：

section:
  id: ipg-section-game-rule-violation
  number: "2.5"
  kind: infraction
  title: { en: Game Rule Violation, zh: 违反游戏规则 }
  penalty: warning                 # 显示值集中解析
  components:
    - id: ipg-section-game-rule-violation-definition
      role: definition             # 标签集中解析
      groups:
        - id: ipg-section-game-rule-violation-definition-g001
          type: paragraph
          blocks:
            - id: ipg-section-game-rule-violation-definition-b001
              en: "..."
              zh: "..."
              provenance:
                officialPdfUnit: ipg-pdf-20240923-p13-u001
  publicationAnnotations:
    - id: ipg-section-game-rule-violation-ann001
      anchor:
        targetKind: component
        targetId: ipg-section-game-rule-violation-additional-remedy
        position: inside-start
        order: 10
      appliesTo:
        - ipg-section-game-rule-violation-additional-remedy-b001
        - ipg-section-game-rule-violation-additional-remedy-b002
      sourceVersion: aipg-2024-09-23-legacy
      en: "..."
      zh: "..."

锚点规则：

  • targetKind 可为 section、component、group 或 block；targetId 必须存在且类型一致。
  • position 为 before、after、inside-start 或 inside-end；容器可使用 inside 位置，叶节点 block 只能 before/after。
  • 同一锚点和位置的多个注解按持久化 order 排列；order 只用于显示，不作为 ID。
  • appliesTo 可选，用于表达注解语义覆盖范围，与显示锚点分离；不得用它代替锚点。
  • 锚点删除或类型变化会产生 orphan finding。candidate 可在独立未决清单中保留，release 中必须为零。

章节、component、group、block 和发布注解都有稳定 ID；Appendix A 使用 sectionRef + penalty code；Appendix B 使用日期分组和可选 sectionRef。

9. 稳定 ID 的完整生命周期

src/ipg/id-registry.yaml 是 ID 分配与历史查询的唯一持久事实源；src/ipg/mapping-overrides.yaml 保存版本间人工映射决策。二者的副本与 SHA-256 进入每个快照。

事件处理规则
新增分配器读取 registry 中该 owner/kind 的 nextSequence，铸造新 ID 后立刻递增。语义 ID 仅用于 section/component；group/block/annotation 使用不回收的单调编号。
删除registry 将 ID 标为 retired，记录 lastSeen 和 tombstone；编号永久禁用，不能因内容重新出现而复用。
历史查询registry 保存 firstSeen、lastSeen、编号/标题历史、aliases、状态与 successor/predecessor；命令可从当前 registry 和快照查询任意历史 ID。
人工 overrideoverride 条目必须含 change ID、来源/目标版本、操作、from/to IDs、正文/注解继承策略、理由和操作者；自动对齐不得覆盖显式决定。
改名保持 ID，更新 title，并在 registry 追加 titleHistory；旧标题成为检索 alias。
改号/移动保持 ID，更新 number/父级/顺序，并记录 locationHistory；路由可生成旧编号 alias。
拆分必须人工 override。默认 retire 原 ID 并为所有新节点分配新 ID；若明确指定一个节点为语义连续体，可由该节点保留旧 ID，其余节点获新 ID。译文和发布注解逐目标决定，不自动复制到全部子项。
合并必须人工 override。若指定一个既有节点为连续体，则保留其 ID，其他 ID 标记 mergedInto；否则铸造新 ID 并 retire 全部来源。冲突译文、注解锚点和审校状态必须人工解决。

任何内容哈希、当前序号、标题 slug 或数组位置都不能单独决定既有 ID。解析器只提出候选映射；registry + overrides 决定身份。

10. 迁移覆盖与可追溯性

  1. 官方 PDF 溯源。每个官方英文 block 必须带 officialPdfUnit，能解析到 PDF SHA-256、页码、bbox 和提取单元；这与是否存在旧译无关。
  2. 旧源唯一处置。每个 raw unit 必须恰好处于 mapped、ignored-with-reason 或 unresolved。一次显式 split 可在一个处置记录中列出多个 target IDs，但不能让同一 raw unit 被两个独立决定重复消费。
  3. 映射是部分函数。一个官方 block 可以没有旧译映射；此时 zh 保持空白并产生 missing-translation。不得要求每个官方 block 都来自旧文件，也不得把英文复制到中文。
  4. 歧义。一个官方 block 若出现多个旧译候选，candidate 记录 unresolved-mapping；只有人工 override 后才能成为 release。
  5. 发布注解。旧注解 raw unit 映射到 publication annotation；无法确定锚点时保存在 candidate 的 unresolved annotation 清单中，不制造无效引用。
两套覆盖公式。
旧 raw unit 总数 = mapped + ignored-with-reason + unresolved，集合两两不相交。
官方 block 总数 = 有旧译映射 + 无旧译映射（missing-translation）。
所有官方 block 都必须有 PDF provenance；只有“有旧译映射”的 block 才必须有旧 raw unit 来源。

11. Candidate 与 Release 两级验证

级别允许必须满足
candidate空中文、未决映射、孤立发布注解、重复消费 finding、未审或 stale 状态；这些内容可留在报告或专用 unresolved 文件中。schema 和引用结构有效；每个官方 block 有 PDF provenance；每个 raw unit 有唯一处置记录；所有 readiness 问题完整计数并带来源；报告总数可重算，不能隐藏或丢弃。candidate 校验成功表示“可审阅”，不表示“可发布”。
release只允许 schema 明确列出的非翻译字段为空；术语 finding 仍为非阻塞。candidate 全部结构门槛；missingTranslation = 0、orphanPublicationAnnotation = 0、unresolvedMapping = 0、duplicateConsumption = 0；受控显示值齐全；发布范围内无 stale 审校记录；许可与署名门槛完成；确定性构建和输出校验通过。

命令界面必须显式选择 --profile candidate 或 --profile release。profile 不读取 manifest，也不写回内容源；source schema 可表达空译文，严格发布条件由跨文件语义验证器执行，避免为了 candidate 复制两套 schema。正式发布入口只能调用 --profile release。

P1 顺序
最小 Vertical Slice		实现只覆盖夹具的解析器与旧源分词器；生成第 2 章 candidate、附录 A/B 小样；完成 candidate/release 验证、原生 JSON 与含发布注解的 IPG.md。2.5 的处罚、组件、列表、发布注解和多层锚点可表达；附录两种结构可表达；构建确定。
P2 顺序
完整审校闭环与人工门槛		在同一 slice 上完成 OmegaT 导出、最小回写、TMX 翻译批注独立归档、review ledger、状态报告、术语审计和发布注解渲染；形成审阅包供用户确认。见第 13 节。未获得模型与阅读效果确认，不进入 P3。
P3 顺序

P4 可分章推进

P4.5 已接通
全文 OmegaT 闭环		全文 PO、阅读句段与交错注解、独立批注和版本化审校账本、预览与最小回写、候选构建及一键助手。回写安全与三类审校数据隔离；接通不表示已完成全文人工审校。
P4.6 当前阶段
本地生产链路		当前 release 指针、正式命令、严格 release gates、隔离演练、两次构建、独立输出校验及整目录 dist 提升；普通中文收尾菜单。成功/失败隔离测试；真实源仍被拦截，真实 dist 不生成；完成审阅后停止。
P5 顺序
官方更新与快照		完成三版本轴快照、精确 diff、ID/译文/发布注解继承和同日换包处理；先本地合成更新测试。新增、删除、改名、改号、拆分、合并、失锚均有测试和人工 override 路径。
P6 顺序
GitHub、CI、Release、文档		仅在本地试制通过后添加 GitHub 远端并确定托管分支策略，加入 CI、定时检查、Draft PR、Release、README 和一键助手。全新 checkout 可复现；Release 标识包含三版本轴和输出哈希；重复发布幂等。

证据包必须提交的材料验收点

迁移对应旧源 raw units、唯一处置账本、映射/缺译/未决/重复消费报告、已知 3246/3248 异常测试。旧源覆盖公式成立；无旧译的官方 block 留空而非伪造来源。

构建与阅读pilot/outputs 中的候选 IPG.md 与 rules.json、两次构建哈希、输出 schema 验证报告；不占用正式 dist。发布注解按 section/component/group/block 锚点及 position 正确渲染；阅读层级获用户确认。
OmegaT 回写source/target PO、import preview、隔离 candidate、应用前后 YAML 最小 diff；受控显示值仅各出现一次。仅选定 zh 标量改变；未知/缺失 ID、英文变化或预览后变化会阻止写回。
翻译批注回写含一条修改理由的 TMX、独立 translation-notes JSON、stale 示例。批注与 unit/hash 关联；不进入内容 YAML、IPG.md、rules.json 或 review ledger。
审校状态独立 ledger 和状态报告，展示 unreviewed、reviewed-unchanged、reviewed-modified、stale。账本没有 note/annotation 字段；译文变更会令记录 stale。
两级门槛一份含声明缺译/未决的 candidate 成功报告；同一状态下 release 失败报告；清零后的 release 成功报告。“可审阅”和“可发布”不可混淆，四个 release 计数均为零。
P2 人工停止点。审阅包完成后暂停。只有用户确认模型、ID、版本展示、IPG.md 阅读效果、发布注解位置及三套审校数据隔离均符合预期，才扩展全文解析器。

16. 风险与缓解

风险影响缓解
在模型确认前写全文解析器大量代码绑定错误抽象。强制 P2 人工停止点；P0/P1 只支持 slice 和小夹具。
三种“注释”混用审校理由泄漏进发布内容或发布注解被当状态元数据。独立路径、schema、命令和测试；构建器只读正式内容 YAML。
旧 AIPG 标记不一致正文与发布注解错分。官方 PDF 优先；raw 覆盖账本；已知异常回归；candidate 保留未决。
官方 PDF 版式变化错切段、漏处罚。几何夹具、PDF provenance、TOC/正文交叉校验和未知结构 fail closed。
ID 拆分/合并误继承中文、发布注解或历史链接错误迁移。registry 永久记录，split/merge 必须人工 override，默认不批量复制。
注解许可或署名不清不能正式发布。不阻塞本地 P2，但 release validator/发布清单必须有合规完成标记和 attribution。
candidate 被误当正式版本缺译或孤立内容发布。产物显著标注 profile；Release 只接受 release validation 报告及四个零计数。

17. 回退、环境与部署边界

  • P0–P2 只在本地 Git 仓库工作，不配置远端、不发布；五个里程碑提交分别提供原始基线、基础模型、解析迁移、构建输出和 OmegaT 闭环的审查与回退点。
  • 迁移与更新始终先写不可变快照和隔离 candidate；正式 release source 只在 release 校验通过后物化。
  • OmegaT 使用 preview → candidate → 完整验证 → --apply --expected-change-count N；翻译批注和状态账本在内容写回成功后分别更新，任一失败都不得伪装成完整成功。
  • 正式内容可重建 dist；translation-notes 和 review ledger 可从各自历史文件恢复，但不参与内容重建。
  • GitHub Actions、自动更新和 Release 属于 P6；所需唯一平台权限预计为仓库自带 GITHUB_TOKEN，不在本地试制中引入外部 secrets。

18. 验收标准（Definition of Done）

  1. P2 前没有全文解析器；slice 能独立证明模型、阅读效果和三套审校数据隔离。
  2. source/output schema 可表达 IPG 处罚、组件、附录、多层发布注解锚点和三版本轴；中央显示值不会在每次出现时产生翻译单元。
  3. 每个官方 block 有 PDF provenance；每个旧 raw unit 有唯一处置；无旧译的官方 block 留空并报告。
  4. candidate 可带完整报告的缺译和未决内容；release 的缺译、孤立发布注解、未决映射和重复消费全部为零。
  5. ID registry 支持新增、不复用、历史查询、override、改名、改号、拆分和合并，且快照能证明所用 registry/override 版本。
  6. dist/IPG.md 同时正确呈现正文与发布注解；dist/rules.json 符合 ipg-output-v1；两次构建字节一致。
  7. OmegaT 回写只改选定中文；TMX 翻译批注归档到独立 store；review ledger 独立记录状态；三者不会互相写入字段。
  8. P2 审阅包获用户确认后才开展 P3；全文完成后再配置 GitHub 与 Release。
  9. 正式发布前补齐注解许可/署名，并通过 release validation、完整测试、确定性构建和文档复现。

19. 实施交接摘要

实施从 P0 开始：初始化本地 Git，重新记录官方 PDF 下载时间和哈希，只制作第 2 章、2.5 与附录 A/B 小夹具；随后完成最小解析、迁移、构建和 P2 审校闭环。P2 审阅包交付后必须暂停，等待用户确认，再决定是否扩展全文。GitHub 远端、CI 和 Release 均不在本地试制范围。

20. 仍需用户决定且会阻碍试制的问题

当前本地流程无新增内容决策。12 项缺译、正式人工审校、注解授权/署名仍须后续完成；不在 P4.6 自动处理。

21. P4.6 本地生产链路契约

功能调查见 MTR/IPG 功能对照表，日常操作见 中文使用说明。统一命令和包装形式与 MTR 对齐，但不复用其 PDF 解析器、日期型版本号、内容节点或 JSON 字段形状。

唯一版本入口与持久化事实源

  • src/ipg/current-release.txt 指向三版本轴组合的完整 release ID。正式命令从该指针读取 manifest，不推测最新目录，不多处硬编码当前 release。
  • src/ipg/version-notes.md 同时进入 Markdown 和 JSON；属于构建输入，也纳入构建期间输入变化检查。
  • 审校状态只读取 review/status/<translation-revision>.json；修改理由保持在 review/translation-notes/<translation-revision>.json，动作在 review/actions/<translation-revision>.yaml。正式构建不改写这些文件。
  • review/migration/<release-id>.json 保存可提交的迁移完成契约，绑定 PDF、旧源 SHA-256 和已有 P4 精简证据文件的路径/哈希；实际核对覆盖数而非假定迁移成功，不依赖可删除的 work 或临时报告。
入口作用产物范围
ipg-validate --profile candidate|release
scripts/validate.py		读取当前指针，核对 schema、引用、注册身份、权威快照、覆盖证据和审校账本；普通中文说明阻塞原因。只读检查，无 dist 写入。
ipg-build --profile candidate完整报告 readiness 问题，不伪装可发布；必须写入 outputs 的新目录。candidate：显著不可发布标记，保留旧候选。
ipg-build --profile release --rehearsal使用与正式构建相同门槛，但不提升到 dist；成功测试采用标明 TEST ONLY 的隔离合成工程。release rehearsal：outputs，无正式发布含义。
ipg-build --profile release
scripts/build.py		通过全部 release 条件后，在临时目录构建两次，分别校验输出，逐字节比较，再整目录提升。正式 dist：仅 IPG.md、rules.json。
ipg-validate-output --input <rules.json>
scripts/validate_output.py		从指针核对 releaseId，独立读取输出并按 ipg-output-v1 校验；不重复审校门槛，不假定 builder 正确。只读，无内容迁移或重建。

发布硬门槛与失败保护

release 只接受全文正文及全文发布注解范围、publishable=true；缺译、未决映射、重复消费、延期/孤立注解均须清零；许可与非空署名完成；每个当前翻译单元恰好一条有效审校记录，unreviewed/stale/孤立/重复记录为零且 sourceHash/targetHash 精确相符。术语词表缺失、解析失败或 finding 均仅报告，不成为发布门槛。候选验证成功不能代替 release 检查。

全部源检查、输出检查、两次确定性比较及构建期间输入变化检查发生在 dist 更新之前。构建哈希在外部报告/控制台/演练证据中，不写入 rules.json，也不作为它的输入。助手选项 5 只读检查，选项 6 调用 release 构建；条件不足列出中文原因，选项 2 的候选流程仍可用。

Windows 目录事务的实际保证。首次 dist 创建是单次目录重命名。已有非空 dist 采用写锁、旧目录可恢复备份、完整新目录提升和出错回滚，绝不逐文件混合更新；两次重命名间可能短暂不存在 dist 路径，并非内核级无间隙 rename-exchange。恢复失败保留完整旧目录并明确报告位置，遗留锁/备份阻止后续覆盖。若未来要求并发网站读者完全无间隙，应另行批准版本目录与读取指针方案；不能把本实现宣称为那种原子性。

证据、停止点及后续差异

自动测试在隔离目录证明 release 成功、版本说明双输出、独立 schema、确定性、整目录更新、失败保持旧文件、输出损坏/二次不一致/输入变化/锁冲突拒绝和恢复失败保留证据。真实工程仅执行只读 candidate/release 检查，现有用户账本、OmegaT、候选目录与快照保持原样。GitHub Release 是未来分发事件，不等于本地 release profile、rehearsal 或 dist。P4.6 审阅包完成后停止；官方更新自动化、全文人工审校和 GitHub 发布仍需单独授权。
